# 기능 명세서

## 공통 응답 형식

```java
@JsonInclude(JsonInclude.Include.NON_NULL)
public class ApiResponse<T> {
    private boolean success;
    private String message;
    private T data;
    private Object meta;
    private String code;
}
```

모든 예외는 @RestControllerAdvice에서 전역 에러코드로 매핑해 ApiResponse.error(code, message)로 반환한다.

### 화면

| 코드 | 화면                                                  |
| ---- | ----------------------------------------------------- |
| S-01 | 로그인 / 회원가입                                     |
| S-02 | 질문 목록                                             |
| S-03 | 질문 상세 / 답변                                      |
| S-04 | 질문 / 답변 작성, 수정                                |
| S-05 | 마이페이지                                            |
| S-06 | 권한 UX ( 401 / 403 안내 )                            |
| S-07 | 신고 목록 조회, 개별 신고 처리                        |
| S-08 | 전체 회원 목록 조회, 신고 누적 확인 후 회원 정지/해제 |
| S-09 | 구독 결제 (멤버십 페이지)                             |
| S-10 | 채팅 화면                                             |

### F-01 회원가입

| 항목       | 내용                                                        |
| ---------- | ----------------------------------------------------------- |
| 액터       | GUEST                                                       |
| 사전조건   | 동일 아이디/닉네임이 없어야함                               |
| 입력       | username, password, nickname                                |
| 처리       | 비밀번호를 BCrypt로 암호화해 저장. 역할은 기본 USER         |
| 출력(성공) | 201 + { username, nickname }                                |
| 예외       | 아이디 / 닉네임 중복 → 409 / 형식 오류 ( 빈 값 등.. ) → 400 |
| 관련 화면  | S-01                                                        |
| 관련 API   | POST /api/auth/signup                                       |

### F-01-1. 아이디/닉네임 중복 확인

| 항목       | 내용                                                       |
| ---------- | ---------------------------------------------------------- |
| 액터       | GUEST                                                      |
| 사전조건   | -                                                          |
| 입력       | username 또는 nickname                                     |
| 처리       | DB 내 중복 여부 조회                                       |
| 출력(성공) | 200                                                        |
| 예외       | 이미 존재 → 409                                            |
| 관련 화면  | S-01                                                       |
| 관련 API   | GET /api/auth/check-username, GET /api/auth/check-nickname |

### F-02. 로그인

| 항목       | 내용                                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| 액터       | GUEST                                                                                                 |
| 사전조건   | 가입된 계정이 존재해야함                                                                              |
| 입력       | username, password                                                                                    |
| 처리       | 비밀번호 검증 후 Access / Refresh Token 발급. Refresh Token은 Redis에 저장하고 httpOnly 쿠키로 내려줌 |
| 출력(성공) | 200 + { accessToken, tokenType: “Bearer” }, Set-Cookie로 refreshToken 전달                            |
| 예외       | 아이디 / 비밀번호 불일치 → 401 / 탈퇴한 계정 → 401 / 정지 계정 → 401                                  |
| 관련 화면  | S-01                                                                                                  |
| 관련 API   | POST /api/auth/login                                                                                  |

### F-02-1. 토큰 재발급

| 항목       | 내용                                                |
| ---------- | --------------------------------------------------- |
| 액터       | USER, ADMIN                                         |
| 사전조건   | 유효 Refresh Token 쿠키 보유                        |
| 입력       | -                                                   |
| 처리       | Redis 내 refreshToken과 대조 후 새 accessToken 발급 |
| 출력(성공) | 200 + { accessToken }                               |
| 예외       | 쿠키 없음/유효하지 않음 → 401 / 만료 → 403          |
| 관련 화면  | -                                                   |
| 관련 API   | POST /api/auth/reissue                              |

### F-02-2. 로그아웃

| 항목       | 내용                                                       |
| ---------- | ---------------------------------------------------------- |
| 액터       | USER, ADMIN                                                |
| 사전조건   | 로그인 상태 ( 유효한 Access Token )                        |
| 입력       | - ( 토큰이 헤더에 )                                        |
| 처리       | Redis에서 해당 Refresh Token 삭제 + refreshToken 쿠키 삭제 |
| 출력(성공) | 200                                                        |
| 예외       | 이미 로그아웃된 토큰 재사용 → 401                          |
| 관련 화면  | S-05                                                       |
| 관련 API   | POST /api/auth/logout                                      |

### F-05. 권한 분리 (USER/ADMIN)

| 항목       | 내용                                                                                                                             |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 액터       | ADMIN                                                                                                                            |
| 사전조건   | 로그인 상태 + ADMIN role                                                                                                         |

| 출력(성공) | 200 + 대상 리소스 JSON ( 기능별로 상이할 것 )                                                                                    |
| 예외       | 비관리자가 접근 → 403                                                                                                            |
| 관련 화면  | S-06 ( 403 권한 오류 안내 )                                                                                                      |
| 관련 API   | /api/admin/\*\*                                                                                                                  |

### F-08. 질문 상세 조회

| 항목       | 내용                                                                                     |

### F-09. 질문 수정/삭제

| 항목       | 내용                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------- |
| 액터       | USER(본인), ADMIN                                                                                             |
| 사전조건   | 유효 JWT                                                                                                      |

### F-10. 질문 - 태그 연결

### F-12. 답변 작성

### F-13. 답변 수정/삭제

### F-14. 답변 채택

| 항목       | 내용                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------- |
| 액터       | USER(본인)                                                                                  |
| 사전조건   | 로그인, 본인이 작성한 질문의 답변만 채택이 가능, 질문의 상태가 아직 “해결됨”이 아니여야 함. |

| 예외       | 질문자 본인 아님 → 403 / 이미 해결된 질문을 재채택 시도 → 409                               |
| 관련 화면  | S-03                                                                                        |
| 관련 API   | POST /api/answer/{id}/adopt                                                                 |

### F-30. PortOne V2 결제 연동

| 항목     | 내용                                                                                 |
| -------- | ------------------------------------------------------------------------------------ |
| 액터     | USER                                                                                 |
| 사전조건 | 유효한 JWT                                                                           |
| 입력     | planType(구독 등급), billingKey(카드 등록 후 PortOne이 발급)                         |
| 처리     | (1) 빌링키 발급 준비: 서버가 카드 등록에 필요한 storeId, channelKey, issueId를 반환. |

(2) 빌링키 발급창: 프론트가 PortOne SDK(`PortOne.requestIssueBillingKey`)로 카드 등록창 호출, 사용자가 카드를 등록하면 PortOne이 billingKey를 발급.
(3) 빌링키 발급+즉시결제: 프론트가 발급받은 billingKey와 planType을 서버로 보내면, 서버가 planType 기준 금액(PREMIUM 4,900원)으로 해당 billingKey로 즉시 결제를 실행하고 성공 시 Subscription에 billingKey를 등록, Payment를 PAID로 저장.
(4) 웹훅: PortOne이 결제 상태 변경 시 호출하는 웹훅을 서명 검증(서명 헤더가 없는 요청은 검증을 생략하고 재조회 경로로 처리) 후 재동기화.
(5) 취소: 결제한 본인(또는 ADMIN)이 취소 요청 → Payment가 PAID 상태인지 확인 → PortOne 결제취소 API 호출 → 성공 시 Payment를 CANCELLED로 반영하고 연결된 Subscription을 즉시 `cancel()` 처리(잔여 기간을 유지하지 않고 즉시 비구독자로 전환). PortOne 관리자 콘솔에서 직접 취소된 경우에 웹훅(`Transaction.Cancelled`)으로 수신해 동일한 동기화 로직으로 반영. 결제 성공 시 F-31(구독 등급 관리)의 Subscription 갱신 트리거. |
| 출력(성공) | 발급 준비: 200 + `{ storeId, channelKey, issueId }` / 발급+결제: 200 + `{ paymentId, planType, status: "PAID", paidAt }` / 최근 결제 조회: 200 + 동일 형태 / 취소: 200 + `{ paymentId, status: "CANCELLED", cancelledAt, reason }` |

### F-33. Github 로그인

| 항목     | 내용                                                                                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 액터     | GUEST                                                                                                                                                           |
| 사전조건 | -                                                                                                                                                               |
| 입력     | 없음(GitHub 인가 코드 교환은 Spring Security OAuth2 Client가 처리) → 신규 가입 시 프론트가 `{ signupToken, nickname }`을 `POST /api/auth/oauth/complete`로 전송 |
| 처리     | GitHub 인증 완료 후 `OAuth2SuccessHandler`가 provider+providerId로 기존 회원을 조회.                                                                            |

기존 회원이면 JWT를 발급해 `302 Redirect → {frontendUrl}/oauth/callback?accessToken=...`로 응답.
신규 사용자면 계정을 바로 만들지 않고 1회용 signupToken을 발급해 `OAuthSignupInfo`로 임시 저장한 뒤 `302 Redirect → {frontendUrl}/oauth/nickname?signupToken=...&nickname=<GitHub login 기반 제안닉네임>`으로 이동시켜 사용자가 닉네임을 확정하게 한다.
프론트가 확정된 닉네임으로 `POST /api/auth/oauth/complete`를 호출하면 이때 `User`가 생성된다(`username`은 `github_{providerId}` 형태로 자동 생성해 기존 회원과 충돌 방지, 닉네임은 사용자가 입력한 값 그대로 사용하며 중복 시 거부) |
| 출력(성공) | 리다이렉트 → 가입 완료 API만 200 + `{ accessToken, tokenType: "Bearer" }`(F-02와 동일 응답 포맷, refreshToken은 쿠키로 전달) |
| 예외 | GitHub 인증 실패 → 소셜 로그인 실패는 프레임워크가 처리 / 정지, 탈퇴 계정 → `401` 대신 `302 Redirect → {frontendUrl}/login?error=SUSPENDED_ACCOUNT`(또는 `WITHDRAWN_ACCOUNT`) /
